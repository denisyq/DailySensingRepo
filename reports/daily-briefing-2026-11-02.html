Netflix TV 端云游戏：官方口径确认「不支持物理手柄」，2027 手柄策略必须重估

Netflix 帮助中心口径（多个第三方整理站于 2026-08 至 10 交叉核查一致）：TV 与电脑端的 Netflix 游戏仍为 beta，TV 端玩法是「电视渲染 + 手机/平板扫码当手柄」，官方明确写明 physical gamepads and other controllers are not supported（含 Xbox 手柄）；iPhone/iPad 需 iOS/iPadOS 17+ 并安装 Netflix Game Controller App，Android 需装有 Netflix App；每位玩家各需一台手机/平板；官方建议下行 ≥10 Mbps（为建议值非保证值）。TV/PC 游戏可用国家共 20 个（美/加/英/德/法/西/意/墨/巴/澳/新等，不含中国大陆）。机型自查入口为 App 内「管理访问权限和设备 → 显示兼容游戏的设备」。

影响

🟡 值得跟踪

WebHID 仍是社区组草案、仅 Chromium 实现：不能作为 TV 端手柄能力的规划基础

WebHID 由 Web Incubator Community Group（WICG）发布，并非 W3C 标准，且目前只有 Chromium 实现；业界实践建议明确将其定位为「progressive enhancement，never as a foundation」。其固有约束还包括：只能在标签页内工作（约 30% 浏览器覆盖）、无后台运行、每次接入新设备都要弹选择器。相对地，Gamepad API 的浏览器覆盖约 97%。这也是为何云游戏/外设方案普遍把 WebHID 当作「读原始报告（陀螺仪、触摸板、自适应扳机）」的增强通道，而把标准按键映射交给 Gamepad API。

影响
三星若在 2027 做「高端手柄特性（陀螺仪/自适应扳机/触摸板）」，不能指望 WebHID 成为跨平台方案——它既非标准，TV 端浏览器覆盖也不由 Chromium 桌面份额推导。可行路径仍是：Tizen 原生手柄框架 + 平台侧认证白名单，Web 侧只走 Gamepad API 的标准映射。
规范现状（非新闻） 覆盖：仅 Chromium 实现；Gamepad API 覆盖约 97%
来源：Universal Controller MIDI 技术博客（从业者整理）· midi.aidxn.com
⚪ 背景参考

Web 设备访问 API 家族（WebHID / WebUSB / Web Serial / Web Bluetooth）正在把浏览器变成「设备交互中心」，但 TV 端缺的是平台授权通道

Web Device APIs 的整体驱动力是把 IoT、教育、零售 POS、工业等场景中「非标准小众硬件」的接入成本从「每个平台一个客户端」降到「一个网页」。这套 API 的价值在于绕开原生驱动，但前提是浏览器对设备的独占/共享访问、权限模型与用户手势授权在目标平台上被实现。

影响
TV 端的缺口不在规范，而在平台层是否把 USB/Bluetooth HID 的访问权开放给 Web 运行时。若 2027 想在 Tizen 上支持「摄像头/麦克风/游戏手柄/遥控配件」的 Web 化接入，需要平台侧给出明确的授权策略（是否需用户手势、是否允许独占、是否列入认证清单），否则 CP 无法据此开发。

🟡 值得跟踪

维持中的门槛口径（往期已闭合，本期无变化）

  • 4K 硬门槛：Widevine L1（硬件 TEE）+ PlayReady SL3000 + HDCP；L3 / SL2000 仅能到 SD/HD。三星官方规格页已确认 Tizen 10.0 = Widevine Modular L1 v18.5 + PlayReady v2.5(SL2000)/v4.5(SL3000)；Tizen 9.0 = Widevine v18.1；8.0 = v17.1。
  • CMAF / cbcs：自 Tizen 5.5（2020 机型）起才支持，意味着 CP 全面切 CMAF 后，2019 年前机型将功能性失效。
  • AV1：建议从「加分项」升级为入门 4K 的一票否决项（YouTube 目录观看时长已超 90% 为 AV1）。

Compute Pressure API 进入 CRD（W3C 2026-10-26）：Chromium 已实现，但 WebKit 明确反对、Mozilla 待定，且 Chrome for Android 不支持

W3C Devices and Sensors Working Group 于 2026-10-26 发布 Compute Pressure Level 1 候选推荐草案（CRD）。规范状态原文：「This specification is implemented in Chromium-based browsers. WebKit has published a position opposing this specification. Mozilla's position is pending.」退出 CR 阶段需在实现报告中记录至少 2 个独立实现。兼容性实况：Chrome 桌面 125+ / Edge 125+ 支持；Chrome for Android 记录为不支持；Firefox、Safari 均不支持；MDN 标注为实验性、Limited availability。规范要求：需安全上下文（HTTPS）、由 compute-pressure Permissions-Policy 管控（默认 allowlist 为 self，禁止第三方调用）、支持 Window/Worker/SharedWorker、不支持 Service Worker。API 只暴露四个高层状态（nominal / fair / serious / critical），不暴露具体硬件阈值，且要求状态仅在实质变化时跳变（防抖）。

影响
这是台账连续跟踪项的关键闭合，且结论为负面可用：① 它曾被寄望成为低端机型「自适应渲染预算」的标准杠杆（在 serious/critical 时降级动画、减少图层、限制后台解码），但 WebKit 反对 + Chrome for Android 不支持 + Firefox/Safari 不支持，意味着它只能作为 Chromium 家族的增强，无法作为跨平台一致性能力写进平台规格；② 对 Tizen（Chromium 系）而言，桌面 Chromium 的实现路径不等于 TV 端可用——还需确认 Tizen M130 是否实现了 PressureObserver 以及是否连接了真实的平台采集器（PressureObserver.knownSources 只是提示，真正支持与否要 observe() 不抛 NotSupportedError 才算）。建议把它降级为「Tizen 私有能力候选」，不作为对外承诺。
规范状态：CRD（2026-10-26），非最终 Rec WebKit 反对 / Mozilla 待定 / Chrome for Android 不支持 受影响机型档位：仅 Chromium 系，TV 端需实测确认

CSS 新草案 animation-trigger：把滚动触发动画从 JS 下沉到渲染引擎；另有 WebMCP 社区组草案

① CSS animation-trigger（W3C CSS WG 新草案）：允许样式表直接声明动画在特定触发条件（滚动/视图时间线的阈值）下 play / pause / reset / reverse，把过去依赖 scroll 事件监听 + IntersectionObserver + 切换 class 的管道下沉到浏览器渲染引擎，减少主线程开销。需与「scroll-driven animations（进度与滚动位置连续绑定）」区分：animation-trigger 是状态式（二值触发）而非连续 scrub。

② WebMCP（Web Machine Learning Community Group，2026-10-27 社区组草案报告）：让网站向 AI Agent 暴露结构化的「工具契约」（名称、描述、输入 schema、输出格式），使 Agent 不必猜测如何点击页面。明确说明这是社区组草案报告，不是最终 W3C 标准。

影响
① animation-trigger 的价值对 TV 端是低端机型上的动画性能——把滚动触发逻辑从 JS 移到引擎，等于给 2GB 机型省下一部分主线程开销，值得纳入「Tizen 引擎升级收益清单」作为向上游提需求的素材；② WebMCP 目前只是社区组草案且以桌面浏览器「人在环路」为前提，TV 端尚早，但方向值得记录：若未来 CP 用 Agent 做内容发现，TV 端可能要提供等价的能力暴露机制。
草案阶段（均未成 Rec） 状态：CSS WG 草案 / WebML CG 社区组草案报告
